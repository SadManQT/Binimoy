## Implemented

**Delivery and inspection** (`packages/db/src/delivery.ts`)
- `submitDelivery`: the seller submits a versioned package. Each vault item must reference an event the homeserver confirms is the seller's encrypted message in the deal's vault room; each statement item must be declared. A missing mandatory part is `INCOMPLETE_DELIVERY`.
- A new submission supersedes the previous one, marks its inspections `STALE`, and invalidates any unsent authorization that depended on it (INV-07).
- `recordInspection`: the buyer records PASSED, FAILED or UNKNOWN for items whose proof is the buyer's own test. Dependencies are enforced. Every attempt is kept.
- `acceptDelivery`: only the current version, only with every mandatory item PASSED, no open dispute, and the held amount equal to the agreed amount.

**Settlement engine** (`packages/db/src/settlement.ts`), following D.5
1. `createAuthorization`: authorization, reservation (held to reserved) and adapter operations created together under the deal lock.
2. `commitDispatch`: the linearization point. Re-checks state and disputes under the lock, then durably marks authorization and operations as committed.
3. Adapter call with a stable key (`binimoy:<authorization>:<kind>`).
4. `applyResult`: success settles the reservation once; final failure returns it to held; pending or unknown keeps it reserved. A finished operation never changes again.
5. `reconcileOperations`: asks the adapter about every unfinished operation; if the adapter never saw the key, re-sends under the same key.
- `refundOverdueDeliveries`: funded, deadline passed, nothing ever submitted: full refund to the buyer.
- `openDispute`: holds everything not yet dispatched; records whether dispatch had already been committed.
- `mockTransferAdapter` with injectable faults.

**Web and worker**
- Deal page: delivery section (deadlines, package version, each item's inspection state, buyer's pass/fail/cannot-check buttons, accept, settlement state, dispute form). The vault panel has the seller's submission form.
- Worker: no-delivery refunds, reconciliation, dispatch.

## Not built

- **The other authorization paths.** No objective release, mutual resolution or reviewed resolution.
- **Dispute resolution.** A dispute can be opened and holds money. Nothing can resolve or close it, so a disputed deal stays held. That is LP-010.
- **Mock account and license providers** (`mock_account.*`, `mock_license.*` predicates). The account-transfer template therefore cannot complete: its provider-checked items stay pending. Software license and digital files can.
- **Login diagnosis workflow** (B8), inspection deadline consequences, correction-attempt limits.
- **Partial settlement, milestones, holdbacks, fees.**
- Capability registry still lists `secret_vault` as `UNCONFIGURED`; nothing reads it for the accepted-release path.

## Not run

- Independent review of the settlement engine. It is the highest-risk code in the repository and has only been reviewed by its author.
- A real crash (process kill) during dispatch; crashes are simulated by calling the steps separately.
- The browser test in CI.
- Load and soak testing.

## Limitations

- `submitDelivery` has no idempotency key: a double submit creates version 2 superseding an identical version 1. No money effect.
- The vault membership check still happens only at room registration (ADR-004 gap 2).
- The mock transfer adapter succeeds instantly unless a test injects a fault.
- A developer `pnpm dev` started before this change runs an old worker that does not dispatch; restart it.
