## Implemented

- `@lp/contracts`: command envelope schema, stable error codes, event type, money parsing and formatting.
- `@lp/domain`: transition tables for the eight D.3 aggregates, with the roles allowed per command, and `checkTransition`.
- `@lp/db`: `executeCommand`, the single transactional path for state changes, and `createAggregate`.
- Database baseline: `app_user`, `deal`, `deal_party`, `aggregate`, `event` (append-only), `outbox`, `idempotency`. Row level security on all of them.
- `docs/api-contract.md` and ADR-002.

## Problems found and fixed

- The test helper set the schema with a query fired from the pool's connect event. That collided with the first real query on each connection and stalled tests. It now uses the connection `options` parameter, which works through the Supabase pooler.
- Query latency from this machine to `ap-southeast-1` has a median near 90 ms with spikes above one second. The default 5-second test limit was too tight for tests with 25 or more round trips, hence the longer timeouts.

## Limitations

- Only buyer and seller roles resolve. Commands needing a reviewer, appeal reviewer or approver are denied for everyone until LP-010.
- No guards beyond role, state, version and idempotency. Consent, funds, freshness and deadline guards belong to the owning tasks.
- No command payload schemas yet; each owning task adds its own.
- The caller chooses the target state when a command has several. LP-004 needs to decide it from data read inside the transaction and will extend the executor.
- There is no authentication. `app_user` rows are bare IDs until LP-003.
- No requirement in `docs/requirements.json` changed status; LP-002 is infrastructure.
